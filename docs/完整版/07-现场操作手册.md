# 07 现场操作手册

> 会前、会中、会后怎么做

这一部分把前面的原理转化为可直接执行的动作。不要把所有动作都加到每一场会议里，应根据议题复杂度选择。

## 先判断：这场会议需要多完整的方法

不是所有会议都需要完整走完“目的对齐、外化、澄清、建模、决策”的全部步骤。方法使用过重，会把简单同步变成仪式；使用过轻，又会让复杂讨论重新陷入误解。先判断会议类型，再决定最低限度需要哪些动作。

| 会议类型 | 最低需要明确 | 不必过度设计 |
|---|---|---|
| 信息同步 | 发生了什么、影响什么、谁需要采取行动 | 不必进行完整业务建模 |
| 探索讨论 | 问题范围、关键原话、已知事实、待验证假设和停车场议题 | 不必强行在本次形成结论 |
| 方案评审 | 目标、约束、备选方案、风险和比较标准 | 不必重新复述所有背景 |
| 决策会议 | 备选项、证据、取舍、决策权和后续行动 | 不应现场重新收集基础事实 |

## 会前：用一页纸定义讨论

| 项目 | 需要写清楚的内容 |
|---|---|
| 背景 | 什么变化或问题触发了本次讨论？ |
| 核心问题 | 今天真正要回答的1-3个问题是什么？ |
| 预期产出 | 事实清单、问题定义、方案比较、决策或行动计划？ |
| 参与者与角色 | 每个人为什么参加，需要贡献什么？ |
| 已知事实 | 哪些信息已经确认，不需要在会上重新争论？ |
| 边界 | 哪些相关问题不在本次讨论范围？ |
| 决策方式 | 谁决策、如何决策、信息不足时怎么办？ |

## 会中：白板建议分成五个区域

白板区域可以由主持者维护，也可以由专门的记录者维护。在人数较多、议题复杂或权力差异明显的会议中，不建议让同一个人同时承担主要发言、事实记录、秩序控制和最终判断。可以由一人维护目的和顺序，一人负责可视化记录，决策者在事实充分后做取舍。小型会议中可以由一人兼任，但这些责任仍应在意识中分开。

| 区域 | 记录什么 |
|---|---|
| A 当前议题 | 正在解决的问题及其边界 |
| B 原始表达 | 参与者关键原话或最小整理后的表达 |
| C 共同事实 | 已被证据或所有参与者确认的内容 |
| D 判断与假设 | 解释、方案、尚待验证的推断 |
| E 问题停车场 | 相关但不属于当前议题的问题 |

### 主持者可以直接使用的话术

- “我先把你刚才的原话写下来，你看有没有遗漏或偏差。”
- “这句话现在是一个判断。我们先补一下支持它的事实。”
- “这个问题很重要，但和当前议题不是同一层。先放到右侧，当前问题结束后再决定是否开启。”
- “先让最接近现场的人把事实完整讲完，其他观点稍后进入。”
- “这里出现了两个不同的问题定义，我们先不要选方案，先确认究竟在解决哪一个。”
- “现在讨论开始指向个人。我们退回到具体动作、结果和证据。”
- “目前信息不足以做判断。需要补什么信息、由谁补、什么时候回来继续讨论？”

## 会后：不要只发一份流水账纪要

传统会议纪要按发言顺序记录谁说了什么，适合追溯，却不一定支持执行。更有价值的会后产物，应当呈现讨论后形成的共同模型。

| 模块 | 内容 |
|---|---|
| 已确认事实 | 数据、案例、约束和已达成一致的现状 |
| 问题定义 | 本次讨论最终确认要解决的问题 |
| 共同判断 | 基于事实形成的原因分析或方向判断 |
| 仍有分歧 | 不同观点及其依据，不要强行写成共识 |
| 待验证事项 | 缺什么证据、由谁补充、截止时间 |
| 决策与行动 | 决定了什么、谁负责、何时完成、验收标准 |
| 停车场议题 | 本次未展开但需要另行处理的问题 |

## 一个完整示例：企业整改超期讨论

背景：近三个月隐患整改超期数量上升。会议目的不是直接确定一个新功能，而是先判断超期主要发生在哪些环节，并决定下一步优先改业务流程、补数据还是调整系统提醒。

发言顺序可以从最接近事实的运营或专家开始，还原超期案例；再由产品整理当前流程和对象状态；技术说明系统当前能够识别哪些节点；管理者最后根据影响和成本做优先级判断。

**原始表达**

> “企业经常拖着不改，提醒也没有用。”

**外化后的白板内容**

部分企业存在整改拖延；当前提醒未能推动部分企业按期完成。

**澄清后形成的事实**

超期主要集中在责任人变更、材料退回后无人继续跟进、重大隐患复查排期三个环节。不同环节的原因和责任主体不同。

**建模后的行动**

把“隐患”“整改任务”“整改材料”“复查任务”“督办事项”拆成对象；明确每个对象的责任角色、状态和超期规则；先补齐责任人与期限字段，再决定提醒和督办功能。

这个例子说明：如果会议一开始就讨论“要不要增加提醒功能”，团队可能很快得到一个看似明确的方案，却没有解决真正的问题。高质量讨论并不必然更慢；它可能在前端多花一些时间，却能避免团队在错误的问题定义上快速行动，并减少后续返工。

## 案例复盘：真正改变的不是白板，而是决策路径

- 先还原事实，避免把“企业拖延”作为一个笼统原因。
- 把不同超期环节拆开，发现它们对应不同对象、责任人和解决方式。
- 让技术约束在方案形成前进入，而不是功能确定后再否定。
- 把“提醒有没有用”的争论改成“什么节点、对什么角色、触发什么动作”的业务问题。
- 最终行动先补基础字段和责任关系，而不是直接开发一个更响亮的提醒功能。

这也是认知对齐的实际价值：它不保证团队一定选中最优方案，但能够显著减少因为问题定义错误、事实混杂和角色不清造成的低级返工。
