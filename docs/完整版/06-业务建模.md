# 06 业务建模

> 对象、动作、角色、流程：从语言进入业务模型

当讨论已经建立共同事实后，结构化工具才真正发挥价值。它们不是用来替代原始表达，而是用来把共识转化为可以设计、执行和交给AI理解的模型。

## 对象：我们究竟在管理什么

对象是可以被识别、记录、查询、跟踪并拥有状态的业务事物。一个实用判断方法是：它能否拥有独立编号、属性和生命周期。企业、隐患、检查任务、整改材料、复查记录、督办事项都可能是对象。

很多模糊表达把对象和动作混在一起。例如“隐患整改”常被当成一个整体概念，但在建模时，“隐患”是对象，“整改”是围绕隐患发生的动作或过程。只有分开，系统才知道需要存什么、谁能操作、状态怎样变化。

## 动作：谁对什么做了什么

动作描述对象之间发生的变化。高质量动作表达通常包含执行者、目标对象、行为和结果。与“加强、推进、优化、落实”相比，“创建、提交、分派、确认、退回、复查、关闭”更接近可以被观察和记录的真实动作。

> “角色对对象执行动作，使对象从一个状态进入另一个状态。”

## 角色：身份、职位和权限不是同一件事

“张三”是人，“副站长”可能是职位，“隐患复查人”是业务角色，“可以关闭重大隐患”是权限。一个人可以拥有多个角色，同一个角色也可以由不同职位的人承担。

把职位直接等同于角色和权限，会让系统被当前组织安排锁死。业务变化后，只能改代码或重做流程。更稳健的设计，是明确组织归属、业务角色、责任关系与操作权限之间的区别。

## 流程：不是箭头，而是条件、动作和状态

流程不只是把几个框用箭头连接。一个可执行流程必须说明：在什么条件下，由哪个角色，对什么对象执行什么动作，动作成功后进入什么状态，失败、超期、驳回或责任人变化时如何处理。

只描述正常路径的流程适合演示，不适合真实运行。真正暴露业务复杂度的，往往是异常分支：材料不合格怎么办、无人负责怎么办、超期怎么办、重复发现同一问题怎么办。

| 维度 | 核心问题 | 示例 |
|---|---|---|
| 对象 | 我们在管理和跟踪什么？ | 隐患、企业、整改材料、督办事项 |
| 动作 | 谁对什么做了什么？ | 企业提交材料、专家复查隐患 |
| 角色 | 谁可以做、必须做、对结果负责？ | 安全员、复查专家、督办确认人 |
| 流程 | 动作按什么条件和顺序推进？ | 提交→复查→关闭／退回／督办 |

## 并非所有问题都适合只用这四个维度

对象、动作、角色、流程适合分析业务运行和系统设计，但战略问题还需要目标、约束、假设和取舍；组织冲突还需要分析利益、权力和责任。方法的成熟，不是把所有问题强行塞进同一个框架，而是先判断模糊发生在哪个层面。

例如，“我们是否应该进入这个行业”不是一个流程问题。它需要明确目标市场、资源约束、关键假设、不可逆投入以及不同选择的机会成本。再比如，“两个部门为什么无法协作”也不一定是流程设计不清，可能是考核目标冲突、责任和权力不对称，或者某一方承担成本、另一方获得收益。

| 问题层面 | 需要补充的分析维度 |
|---|---|
| 业务运行 | 对象、动作、角色、状态、流程、异常规则 |
| 战略选择 | 目标、约束、关键假设、选项、取舍、不可逆成本 |
| 组织协作 | 利益、权力、责任、激励、信息差、风险承担 |
| 认知分歧 | 事实来源、概念边界、判断依据、价值偏好 |

所以，“从模糊到清晰”的真正原则不是所有事情都对象化，而是识别模糊发生在哪个层面，再选择能够暴露关键差异的结构。
